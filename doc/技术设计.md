# 技术设计

本文件记录当前实现与后续阶段的业务方案。范围与验收条件见 [Spec](Spec.md)。

## 本地架构

Vue 应用由 Vite 启动，开发时将 `/api` 代理到本机 Django。`backend/config/settings.py` 读取根目录 `.env`，通过 psycopg 连接 Docker 中的 PostgreSQL 17。数据库端口只绑定本机，使用 Compose 命名卷持久化数据。

完整容器模式下，`frontend/Dockerfile` 根据 npm 锁文件构建 Vue，由 Nginx 提供静态页面和页面路由回退。Nginx 将 `/api` 转发给 Compose 内网中的 Django。`backend/Dockerfile` 根据 uv 锁文件安装依赖，连接 `db:5432`，自动应用迁移后由 Gunicorn 提供服务。Compose 按 PostgreSQL、Django、Nginx 的健康状态依次启动。完整启动和端口配置见 [README](../README.md#docker-一键启动)。

使用独立 Compose 项目和空 PostgreSQL 卷验证自动迁移、页面与静态资源、Nginx API 代理，以及注册、登录、提交、待办、两级通过和历史查询的 HTTP 流程。容器内运行 `python manage.py test --noinput`，62 项后端测试通过。本地项目使用原有数据卷启动，验证了启动前后用户记录数量一致。

`backend/users/models.py` 的用户模型继承 Django `AbstractUser`，补充昵称并使用 Django 的密码哈希机制。用户模型在首个迁移中建立，后续申请单及历史通过 Django 的用户模型配置引用。申请单与历史的逻辑结构见 [ER 图](ER图.md)，接口契约见 [OpenAPI](../openapi.json)。

## 认证、异常与日志

注册和登录在 `backend/users/serializers.py` 中校验：注册使用模型字段、Django 密码校验器与项目自定义字符类型校验器（至少两类字符），并在数据库事务内创建用户；账号（`username`）存在性检查与数据库唯一约束共同覆盖并发注册，`IntegrityError` 转换为字段级 400。登录使用 `django.contrib.auth.authenticate`，用户不存在与密码错误统一返回 `invalid_credentials`，避免枚举账号。登录成功后使用 Simple JWT 的访问令牌，响应不包含刷新令牌。

`rest_framework_simplejwt.authentication.JWTAuthentication` 负责解析 `Authorization: Bearer`；全局权限保持 `IsAuthenticated`，注册与登录视图显式设置 `AllowAny` 并禁用认证类。`GET /api/users/me` 从 `request.user` 读取当前用户。

`backend/common/exceptions.py` 替换 DRF 默认异常处理，将所有非 2xx 响应统一为 `{code, message, details?}`。预期失败返回可读 4xx 且不记录堆栈；未预期异常由 `common.exceptions` 记录一条 ERROR 日志，包含请求方法、路由、异常类型和脱敏堆栈，客户端收到通用 500。`backend/common/logging.py` 的格式化器会抹除密码、密码哈希、JWT、Authorization 头及配置中的签名密钥和数据库密码。

前端在 `frontend/src/api/client.ts` 统一封装请求并注入 Bearer Token，`frontend/src/auth/store.ts` 管理会话，路由守卫在首次导航时调用 `/api/users/me` 恢复用户。Token 仅存于 `sessionStorage`；收到 401 时清除 Token、用户状态并跳转登录页。

## 草稿管理实现

`backend/approvals/models.py` 建立 `ApprovalRequest`，包含标题、内容、状态、申请人、两级审批人、当前步骤、创建/更新/提交时间。申请人、一级审批人、二级审批人均引用现有用户模型；数据库约束阻止申请人担任任一审批人，限制当前步骤为 1、2 或空，并为“申请人+创建时间”“状态+创建时间”建立索引。`current_approver` 是模型属性，仅在审批中且当前步骤为 1 或 2 时返回对应审批人，不落库。

`backend/approvals/serializers.py` 的 `DraftInputSerializer` 只接收四个可编辑字段，校验非空白、长度、审批人存在性和“不能选择自己”，允许两级选择同一人。`ApprovalRequestSerializer` 输出申请人/审批人摘要、计算后的当前审批人和时间；详情序列化器在本轮固定返回空 `history`，因为尚未建立审批历史模型。创建时申请人来自 `request.user`，状态固定为 `draft`，步骤、提交时间为空；更新使用完整 PUT 并触发 `updated_at`。

`backend/approvals/services.py` 集中判断权限：详情只允许申请人或任一审批人；编辑和删除只允许申请人且状态必须为 `draft`。无权限返回 403，非草稿返回 409。`backend/approvals/views.py` 的列表接口仅实现 `scope=mine`，先按状态/标题关键词筛选，再按 `-created_at, -id` 排序和分页，返回筛选后的 `count`；`scope=pending` 明确返回 400。`GET /api/users` 返回全部用户摘要，前端选择审批人时过滤当前账号。

前端在 `frontend/src/api/requests.ts` 封装草稿接口；`HomePage` 提供列表、筛选、搜索和分页，`RequestFormPage` 复用新建/编辑表单，`RequestDetailPage` 展示详情、草稿入口和删除确认。路由守卫沿用已完成的 JWT 会话恢复和 401 处理。

## 审批实现方案

业务实现阶段，在 `backend/approvals/services.py` 中集中处理提交、通过和驳回。操作在数据库事务内锁定申请单，读取当前状态、步骤和审批人，校验后同时更新申请单和写入历史。其他修改草稿状态或内容的操作使用相同的行锁规则，避免与提交互相覆盖。

通过和驳回接口接收 `expected_step` 并与加锁后读取的当前步骤比较。同一用户处理两个节点时，一级旧请求仍携带原步骤，不能推进已经进入的二级节点。实现后按 [Spec](Spec.md#9-验收条件) 验证越权、历史写入失败回滚，以及重复与并发审批。

### 提交与两级通过（实现进展）

提交、通过在 `transaction.atomic` 内对申请单执行 `select_for_update`，锁定后读取状态与步骤、校验操作人，更新申请单并写入操作历史；历史写入失败时事务整体回滚。草稿编辑与删除也在事务内使用同一行锁，并在加锁后检查状态。审批请求携带页面所见的 `expected_step`，用于拒绝旧步骤的重放；审批人和后续状态均由服务端记录决定。

本地验证：PostgreSQL 迁移成功，后端测试 48 项通过，前端生产构建成功。独立连接并发测试、历史写入失败回滚测试和浏览器端到端验收尚未完成，不能据此认定并发与回滚验收通过。


### 驳回、待办与历史查询

驳回与通过共用申请单行锁、事务和操作历史；驳回意见经去空白校验，成功后进入 rejected 终态。待办同时限制 in_review 状态、当前步骤及相应审批人；独立历史接口沿用详情权限与排序。

本次在 PostgreSQL 上运行事务测试：模拟历史写入失败后，驳回的状态、步骤和时间字段回滚；两个独立连接竞争同一节点的通过和驳回，仅一个成功且只增加一条历史。完整后端测试 52 项及前端构建通过。浏览器一级驳回、二级驳回和两级通过的端到端验收尚未执行；完整筛选分页覆盖及提交、通过的历史写入失败回滚测试尚需补齐。

### 待办筛选、步骤重放与回滚测试（实现进展）

回滚覆盖已扩展到草稿提交、一级通过和二级通过：历史写入失败时，状态、当前步骤、提交时间与更新时间均保持操作前的值，已有历史不变且无新增。同一用户担任两级审批人时，携带旧步骤的请求返回 409，流程停在二级；随后携带当前步骤的请求可正常结束流程。待办列表先按“审批中 + 当前步骤 + 对应审批人”确定范围，再叠加状态与标题关键词筛选，最后分页，`count` 为筛选后的总数；创建时间相同时按 ID 倒序，跨页无重复或遗漏。场景、命令与结果见 [验收记录](验收记录.md#审批流程后端自动化测试补全本轮)。完整后端测试 62 项通过，浏览器端到端验收仍未执行。
