# 简易审批流系统需求说明书（Spec）

## 1. 需求来源与目标

需求来源：《简易审批流系统 — 实习生开发任务书》；技术选型由项目提出人确定。

建设一个前后端分离的简易审批系统，使员工能在浏览器中创建申请、提交固定两级串行审批，并查看处理进度和历史。项目周期为 5 个工作日，优先交付完整审批闭环、权限校验、事务一致性、并发控制及可用的前端页面。

## 2. 技术范围

| 层次 | 选型或要求 |
| --- | --- |
| 前端 | Vue 3，通过 HTTP API 访问后端 |
| 后端 | Django REST Framework，业务逻辑与接口职责清晰分离 |
| 数据库 | PostgreSQL，使用 Django ORM |
| 身份认证 | JWT Bearer，后端验证 Token |
| API 文档 | Swagger / OpenAPI |
| 测试 | 使用适配技术栈的测试工具，覆盖关键业务规则 |
| 运行与交付 | 可在本地复现启动；使用 Git 管理版本 |

前端不得直接连接数据库。密码必须安全哈希存储；不得提交真实密码、密钥或敏感配置。审批规则和权限必须由后端校验。

## 3. 范围与边界

### 3.1 本期范围

- 用户注册、登录、获取当前用户及审批人选择列表。
- 草稿创建、编辑、删除、提交，以及申请详情和列表查询。
- 固定两级串行审批、通过与驳回、待我审批列表。
- 审批历史、权限校验、参数校验和统一异常处理。
- 状态更新与历史写入的事务一致性，以及重复和并发审批控制。
- 浏览器页面、API 文档、数据库初始化、测试和项目文档。

### 3.2 可选扩展

完成全部必做需求后，可选择实现驳回后修改重提、撤回申请、Docker Compose 或额外集成测试。若实现扩展，须在 Spec 中补充规则，且不得破坏基础流程。

### 3.3 本期不要求

通用工作流引擎、流程设计器、会签、转交、加签、动态修改审批人、通知、附件上传、移动端适配和微服务。驳回后修改重提与撤回不属于本期基础流程。

## 4. 用户与权限

系统不要求管理员角色。所有注册用户均可创建申请；能否审批取决于该用户是否为当前步骤的指定审批人。

| 角色或条件 | 可执行操作 |
| --- | --- |
| 未登录用户 | 注册、登录；其他业务接口不可访问 |
| 申请人 | 创建申请；查看自己的申请及历史；编辑、提交或删除自己的草稿 |
| 指定的一级或二级审批人 | 查看参与的申请及历史；仅在轮到本人时审批 |
| 无关用户 | 不可查看申请详情及历史，也不可处理该申请 |

两级审批人均须为已存在用户，且均不能是申请人。一级和二级审批人可以是同一人，但必须分别完成两个步骤。前端根据权限控制操作入口，后端必须独立校验权限。

## 5. 业务数据

### 5.1 用户

注册信息包括用户名、密码和显示名称。用户名唯一；登录使用用户名和密码获取 JWT。

### 5.2 申请单

| 字段 | 要求 |
| --- | --- |
| ID | 唯一标识 |
| 标题 | 必填，最长 100 字符 |
| 内容 | 必填，最长 2000 字符 |
| 状态 | 草稿、审批中、已通过、已驳回 |
| 申请人 | 由当前登录用户确定 |
| 一级、二级审批人 | 已存在用户，均不得为申请人 |
| 当前步骤 | 一级或二级审批；草稿和流程结束时可为空 |
| 创建时间、更新时间 | 分别记录创建和最近更新的时间 |
| 提交时间 | 最近一次提交时间，可为空 |

### 5.3 操作历史

每次成功提交或审批均须记录申请单、操作类型、操作人、审批步骤、意见、操作前后的状态与步骤、操作时间。提交时步骤和意见可为空。历史按操作时间升序返回，同一时间须有稳定的次级排序；普通用户不可修改或删除历史。删除草稿不得产生误导性的审批记录。

## 6. 功能与业务规则

### 6.1 用户注册和登录

1. 用户使用用户名、密码、显示名称注册；重复用户名注册失败。
2. 用户使用用户名和密码登录；密码错误时登录失败。
3. 登录后可获取当前用户信息及用于选择审批人的用户简要列表。
4. 除注册、登录外，业务接口均需认证；未携带有效 Token 返回 HTTP 401。

### 6.2 申请管理

1. 创建申请时状态为草稿，申请人取自当前登录用户。
2. 只有申请人可编辑自己草稿的标题、内容和两级审批人，也只有申请人可提交或删除自己的草稿。
3. 审批中和已结束的申请不可删除；已通过的申请不可再次编辑、提交或审批。
4. 申请详情展示申请内容、申请人、两级审批人、状态、当前步骤、当前审批人及历史。
5. 提供“我发起的”和“待我审批”入口。申请列表支持分页、状态筛选和标题关键词搜索，分页结果返回总条数；待审批列表仅包含当前需要本人处理的申请，草稿不出现在其中。

### 6.3 状态流转

| 当前状态 / 步骤 | 操作及执行人 | 结果 |
| --- | --- | --- |
| 草稿 | 申请人提交 | 审批中，进入一级审批 |
| 审批中 / 一级 | 一级审批人通过 | 仍为审批中，进入二级审批 |
| 审批中 / 二级 | 二级审批人通过 | 已通过，流程结束 |
| 审批中 / 一级或二级 | 当前审批人驳回 | 已驳回，流程结束 |

- 只有草稿可以提交；不得跳过节点、提前审批下一节点或审批已结束的申请。
- 通过时意见可为空；驳回时意见必填。审批意见最长 500 字符。
- 两级审批人相同时，一级通过只推进至二级，仍须再次执行二级审批。
- 基础流程中，驳回后不可修改重提。

### 6.4 事务与并发

- 每次成功提交或审批，申请状态／当前步骤的更新与历史记录写入必须处于同一数据库事务，全部成功或全部回滚。
- 后端依据数据库中的当前状态、步骤和审批人判断操作是否有效，不信任前端提供的当前步骤。
- 已处理步骤的重复请求必须被拒绝且不得新增重复历史；同一节点的并发审批请求最多一个成功。
- 技术设计须说明事务边界、并发及防重复策略，并提供验证步骤；须通过测试或演示证明历史写入失败时状态不变。

### 6.5 参数校验与错误处理

校验必填项、字符串长度、分页参数、审批人是否存在及审批意见等。统一处理异常，返回可读的业务错误；内部异常记录日志，响应不暴露堆栈或敏感数据。

| 情况 | HTTP 状态 |
| --- | --- |
| 参数不合法 | 400 |
| 未登录或 Token 无效 | 401 |
| 无操作权限 | 403 |
| 申请不存在 | 404 |
| 状态冲突或重复审批 | 可统一使用 409 |
| 服务器内部错误 | 500 |

任务书允许无权查看时统一返回 404 以避免资源枚举；本 Spec 暂按 403 表述，若采用 404，须统一并在文档中说明。

## 7. 前端需求

| 页面或功能 | 最低要求 |
| --- | --- |
| 注册、登录 | 输入注册或登录信息，显示校验结果；未登录限制访问业务页面 |
| 我发起的 | 显示标题、状态、当前步骤、创建时间；支持分页、状态筛选、关键词搜索 |
| 新建／编辑申请 | 编辑标题、内容及两级审批人；草稿可保存和提交 |
| 申请详情 | 显示申请内容、申请人、审批人、状态和当前步骤 |
| 待我审批 | 显示当前需要本人处理的申请，可进入详情 |
| 审批操作 | 当前审批人可通过或驳回；驳回意见必填；操作后刷新状态 |
| 审批历史 | 按顺序显示提交和审批操作、操作人、意见及时间 |
| 通用交互 | 加载状态、空数据提示、成功／失败反馈、表单校验和退出登录 |

API 请求须统一封装并携带 JWT，Token 失效时引导重新登录。所有核心业务须可通过桌面浏览器完成，Swagger / Postman 仅作辅助调试。

## 8. 接口能力

路由和 DTO 可在实现时调整，实际接口须体现在 OpenAPI 文档中。

| 方法 | 参考路由 | 能力 |
| --- | --- | --- |
| POST | `/api/auth/register` | 注册 |
| POST | `/api/auth/login` | 登录并获取 Token |
| GET | `/api/users/me` | 获取当前用户 |
| GET | `/api/users` | 获取用户简要列表 |
| POST | `/api/requests` | 创建草稿 |
| GET | `/api/requests` | 分页查询我发起的或待我审批的申请 |
| GET | `/api/requests/{id}` | 查看申请详情 |
| PUT | `/api/requests/{id}` | 修改草稿 |
| DELETE | `/api/requests/{id}` | 删除草稿 |
| POST | `/api/requests/{id}/submit` | 提交申请 |
| POST | `/api/requests/{id}/approve` | 当前节点通过 |
| POST | `/api/requests/{id}/reject` | 当前节点驳回 |
| GET | `/api/requests/{id}/history` | 查看操作历史 |

分页建议默认 `page=1`、`pageSize=10`，最大 `pageSize=100`；最终参数与响应格式须在接口文档和 README 中说明。

## 9. 验收条件

以下场景均须验证；其中第 3、4、7、8 项必须提供自动化测试，第 7 项建议使用集成测试。其他场景可使用测试代码或手动验收记录。

1. 创建后为草稿，只有申请人能编辑和提交。
2. 提交后进入一级审批；草稿不出现在待审批列表。
3. 非当前审批人不能通过或驳回。
4. 一级通过后进入二级审批，不能直接变为已通过。
5. 二级通过后状态为已通过，后续审批被拒绝。
6. 一级或二级驳回后流程结束，驳回意见不能为空。
7. 历史写入失败时，申请状态及当前步骤回滚。
8. 重复审批被拒绝且不产生重复记录；同一节点并发请求最多一个成功。
9. 申请人不能将自己选为审批人。
10. 无关用户不能查看申请详情及历史；未登录访问业务接口被拒绝。
11. 分页结果总条数正确；待审批列表只包含当前需要本人处理的申请。
12. 浏览器可完整完成注册登录、创建草稿、提交、一级审批、二级审批和查看历史。
13. 前端正确显示错误、加载状态和空列表。

## 10. 数据库与交付物

- 数据库至少覆盖用户、申请单、审批历史；提供 ER 图、建表脚本或 ORM Migration、测试数据准备方式，以及主外键和必要索引说明。
- 技术设计说明状态、步骤与历史的关系、审批权限、事务边界、并发防重复及数据库约束，并提供关键代码和 OpenAPI 入口。
- 交付前端、后端、数据库初始化文件、测试代码及结果；README 须包含技术栈、目录结构、配置、初始化、启动和测试步骤、已实现与未完成项，并链接项目文档。
- 提供开发规范，覆盖模块职责、命名与格式化、API 与错误约定、迁移与配置、分支提交、代码审查、测试，以及 AI 生成内容的人工审查和验证。
- 文档随代码维护；验收记录注明环境、命令或操作步骤及结果，未执行项如实标明。新环境应能按 README 完成初始化、启动和测试。

## 11. 假设与待确认事项

- 已确定 Vue 3、Django REST Framework 和 PostgreSQL；具体前端构建工具、JWT 库、API 文档库及测试工具由后续技术设计确定。
- 任务书允许同一人担任两级审批人，同时要求旧请求不能重复推进；如何区分一级旧请求与该用户有意发起的二级审批请求，须在技术设计中明确并验证。
- 任务书要求通过意见可为空、驳回意见必填；本 Spec 按此执行，意见长度上限按 500 字符统一处理。
- 分页默认值和最大值为任务书建议值，具体约定待接口设计确定。
